## 2. 작업 방식 — 반드시 유지할 사용자 규칙

1. **구현 요청에는 구현 프롬프트를 작성하는 방식으로 진행한다.** 2026-10-21 사용자가 “직접 구현하란 게 아닌 프롬프트만 작성”이라고 재확인했다. 직접 코드 수정 권한으로 해석하지 않는다. 설명·계획·보고서 검토는 읽기 전용이다.
2. **빌드와 검증은 사용자가 직접 수행한다.** 에이전트는 Unity 실행, 컴파일, 빌드, 테스트, 자동 탐색·재현 실험, 자동 검증을 수행하거나 이를 수행하도록 구현 프롬프트에 지시하지 않는다.
3. 데이터 `export`, `verify`, `fixture`, Python 실행, 모델 실행도 별도 명시적 요청 없이 수행하지 않는다.
4. 읽기 전용 코드·문서·Git 확인은 가능하다. 코드 검토와 동작 검증은 구분해서 보고한다.
5. 사용자가 구현 프롬프트를 요청하기 전에는 먼저 프롬프트를 작성하지 않는다.
6. 기존 사용자 변경·장면·설정·데이터를 보존한다. 커밋·푸시는 명시적 요청 없이 하지 않는다.
7. “코드 작성 완료”와 “사용자 검증 완료”를 별개로 표시한다. 실행하지 않은 결과를 통과했다고 쓰지 않는다.
8. 방향 표기는 **상·하·좌·우**를 사용한다.
9. 매일 작업 종료 시 `D:\Pro_KW\DebLogs`에 사용자 입장의 개발일지를 작성한다. 무엇을 어떻게 개발했는지, 문제·원인·해결, 확인 범위, 남은 과제를 기록한다. 자동 스케줄 작업은 설정돼 있지 않다.
10. 문서 작성 요청은 문서 생성·갱신 권한이다. 이 경우도 파일 시스템의 허용 범위를 넘는 쓰기는 필요한 경로 권한을 받아 진행한다.
11. **“코드 작성 규칙”은 다음 네 가지다.** 구현 전 가정·불확실성·대안을 밝히고 필요한 질문을 한다. 요청을 해결하는 최소 코드만 작성한다. 필요한 부분만 기존 스타일에 맞춰 수정하고 무관한 정리는 하지 않는다. 성공 기준·짧은 계획·확인 방법을 먼저 정한다. 실행 검증은 2번에 따라 사용자가 수행한다.
12. **Caveman 소통을 유지한다.** 설명은 간결하게 하되 기술적 조건·순서는 생략하지 않는다. 복잡한 절차는 명확성을 우선한다. 커밋 메시지는 제목뿐 아니라 무엇을 했는지 본문도 제공한다. 관련 스킬이 필요하면 읽고 적용한다.

## 7. 3D 방 단계의 확정 사항과 다음 경계

**3단계 3D 방·공유 문·풀링과 루트 수정: 사용자 확인·커밋 완료.** 확정된 설계:

- 방 프리팹(`TestRoomPrefab`)과 문 프리팹(`TestDoor`)을 분리하고 **각각 별도 풀**에서 재사용한다. 프리팹은 사용자가 만들고, 코드는 형태·크기·재질을 바꾸지 않는다.
- 활성 방은 **현재 방 + 상하좌우 중 생성된 방, 최대 5개**. 주변의 주변은 활성화하지 않는다. 미생성 좌표에 방을 만들지 않는다.
- 문은 방 소유가 아니라 **공유 연결당 문 하나**. 좌우는 왼쪽 방의 우 출입구, 상하는 아래쪽 방의 상 출입구 기준. 활성 방의 네 출입구 모두 닫힌 문으로 경계를 막는다(문 존재 ≠ 이동 가능).
- 문은 **자식 본체가 위로 미끄러지는 방식**. 상태는 연결 ID별로 GameObject와 분리 보관한다. 현재 여는 입력·애니메이션은 없고 모든 문은 닫힘.
- 논리 `(x,y)` → `(x×간격, 0, y×간격)`, 상 +Z. 간격 기본은 방 프리팹 메시 크기 자동(TestRoomPrefab 5.2).
- **벽별 다음 방 단어 표시는 후속 `5c6bef4`에서 구현·사용자 확인 완료.** `Wall_Up/Down/Left/Right → WordTag → Word → WordText`의 TMP 3D 텍스트에 표기한다. 미생성은 `미생성`. 현재 방·목표 HUD는 별도 미구현이다.
- 표현 계층은 생성 엔진을 호출하지 않고, 요청 완료 직후 작업 스레드에서 만든 스냅샷만 읽는다.
- 3D 설정(프리팹·문 본체 이름·DoorPoint·보정값·루트·간격)은 새 실험 시작 시 고정한다. 실험 중 Inspector 변경은 다음 새 실험부터 적용한다. 루트가 바뀌면 해당 풀을 정리하고 새 루트로 다시 만든다. 비운 루트는 자동 루트를 만들어 재사용한다. 사용자 루트와 그 자식은 삭제하지 않는다.
- **자동 루트 소유권(`770e6ab`)**: 자동 `Rooms`/`Doors`가 Room Root·Door Root 중 **어느 쪽에서든** 참조되면 사용자 루트로 넘어가 이 컴포넌트가 더 이상 관리·삭제하지 않는다(교차 지정 포함). 전환은 `BeginSession` 맨 앞, 프리팹 설정 확인과 루트 확정보다 먼저 처리하므로 설정 오류 실패 경로에서도 보호된다. `ReleaseAutoRootIfUnused`도 풀 사용 검사·Destroy 판단 전에 같은 확인을 하므로 `OnDestroy`(컴포넌트 제거)에서도 지정 루트를 지우지 않는다. 교차 지정 시 비워 둔 쪽은 새 자동 루트를 만든다. 두 필드에 같은 루트를 지정하는 것은 막지 않는다. 부모 GameObject 자체를 삭제할 때 Unity가 자식을 함께 지우는 동작은 범위 밖이다.
- 출입구는 바닥 윗면 기준 2.2m, 폭 1m. 문 자식 `Door`는 Local Position Y 1.1, Scale Y 2.2. 벽 높이 2.8m는 유지. 자동 열림 상승 거리는 2.2m이나 여는 입력·애니메이션은 아직 없다.
- 현재 `FirstPersonPlayer`는 높이 1.8m, 시점 1.6m, WASD 3m/s, 마우스 감도 0.1, 수직 제한 ±85°. 첫 방 바닥을 Ray로 찾은 뒤 배치한다. 새 실험 동안 `Suspend`로 낙하를 멈춘다.
- 씬의 Main Camera는 Player 자식이며 RoomGenerationDebug.Player에 연결돼 있다. `Show(snapshot, player == null)`로 디버그 카메라 자동 이동을 차단한다. 이 상태에서는 방향키 논리 이동도 차단된다.

**루트 수정 확인 기준**: 사용자가 Unity 확인 완료를 통보했다. 아래는 회귀 확인용 기준이며, 개별 항목별 실행 결과가 별도 기록된 것은 아니다.

1. 자동 `Rooms`를 Room Root에 지정한 뒤 Door Body Name을 잘못 입력하고 새 실험 → 오류만 나고 `Rooms`와 필드 참조가 남는다.
2. 이름을 바로잡고 새 실험 → 같은 루트로 3D 표시가 재개된다.
3. 자동 `Rooms`를 Door Root에, 자동 `Doors`를 Room Root에 교차 지정 → 정상 설정이면 비운 쪽에 새 자동 루트가 생기고, 설정 실패여도 지정 루트가 남는다.
4. 교차 지정 상태에서 다른 쪽 루트를 프리팹 자산으로 지정 → 루트 오류만 나고 지정 루트가 남는다.
5. 지정 루트 아래 사용자 자식 `Note`를 두고 새 실험 → 루트와 `Note`가 남고 풀 인스턴스만 정리된다.
6. 지정 직후 새 실험 없이 RoomWorldView 컴포넌트만 제거 → 지정 루트가 남는다.
7. 루트를 비운 일반 사용에서 새 실험 반복 → `Rooms`·`Doors`가 하나씩 유지되고 풀 인스턴스가 재사용된다.

### 7.1 이동 기능 확인과 별개로 남은 코드 검토 문제

1. **실행 중 Player 칸 해제**: 참조를 비워도 이전 FirstPersonPlayer는 `placed=true`로 계속 동작한다. 방향키·디버그 카메라가 다시 활성화되면 같은 카메라를 동시에 제어할 수 있고, 새 실험 중에도 이전 플레이어가 중력을 적용받을 수 있다. 이전 플레이어 정지·커서 해제가 필요하다.
2. **비활성 플레이어 배치**: `PlacePlayer`는 null만 확인해 비활성 컴포넌트에도 `PlaceAt`을 호출한다. 생성 대기 중 비활성화하거나 비활성 상태로 새 실험을 시작하면 배치 완료 시 커서가 다시 잠길 수 있으나 그 컴포넌트의 Update/Escape 처리는 실행되지 않는다. 배치·모드 판정에 활성 여부 기준이 필요하다.

두 항목은 코드 읽기에서 확인한 경로이며 실행 재현하지 않았다. `cf1dd59`에도 수정되지 않은 채 남아 있다. 사용자의 이동 검증 완료를 이 두 항목의 수정·통과로 해석하지 않는다. 디버그 방식 확인은 우선 **Play 종료 후** Player 연결을 비워 다시 시작한다. near clip 0.3의 벽 근접 잘림은 시각 확인·조정 후보이며 확정 버그는 아니다.

**다음 기능**: 문 열기 상호작용·상승 애니메이션 → 실제 문 통과 시 정확히 한 번 논리 이동·방문 처리 → 빈 주변 생성·방/문/표지판 갱신. E키는 제안이며 문 열기 세부값과 생성 중 출입 정책은 후속 합의 대상이다. 전환 문제 2건을 수정할 범위도 구현 프롬프트 작성 전에 구분한다. 이후 단독 흐름, Photon, 재접속·인계, 공유 지도·그림이 남아 있다.

## 8. 다음 세션이 놓치기 쉬운 사항

- 일반 플레이는 무제한. 테스트에서만 `UseMoveLimit=true`로 제한한다. `MaxMoves=300` 자체가 제한 활성화를 뜻하지 않는다.
- 중복 금지는 **후보 좌표 기준 맨해튼 거리 3 이하**다. 생성 개수 3개와 다른 개념이다. 공통 `RepeatRadius`를 사용하며 게임 규칙은 3으로 확정됐다.
- 과거 보고서의 “fastText 임시 배치는 거리 3 하드코딩”은 현재 코드와 다르다. 이미 `RepeatRadius`를 참조한다.
- 목표 도착은 표기 일치다. 동음이의어의 특정 뜻으로 도착해야 하는 게임으로 바꾸지 않는다.
- 4방향을 채우는 것이 요구사항이지만, 현재 엔진에는 후보 부족·취소·실패로 미생성이 남는 상태가 있다. 생성된 방의 출입을 막거나 항상 완성됐다고 숨기지 않는다.
- Python과 같은 시드가 같은 지도를 보장하지 않는다. float32 내적·합산·지수 계산의 미세 차이로 후보 순서가 달라질 수 있다.
- 현재 `RoomMap`은 현재 위치·이동 수·경로가 하나다. 여러 플레이어를 그대로 한 `Move`에 연결하면 서로의 위치를 덮어쓴다. 멀티 단계에서 **공유 월드와 플레이어별 상태를 분리**해야 한다.
- 호스트에게 요청하는 구조는 합의됐지만, 재접속·인계·스냅샷·RPC 형식은 아직 구현되지 않았다.
- 3D 풀에 방·문을 반환해도 논리 지도(RoomMap)와 문 상태는 지워지지 않는다. 새 실험 초기화와 표시 범위 이탈을 구분한다.
- TestRoomPrefab의 DoorPoint는 같은 이름 4개이고 벽 자식이며, 문 중심이 아닌 출입구 모서리다. DoorPoint 회전을 그대로 복사하면 좌 출입구에서 문이 빗나간다.
- 게임 저장 없음은 영구 세이브 없음이다. 세션 안의 지도 유지와 재접속용 상태 보관까지 없애라는 뜻이 아니다.
- 사용자의 최신 결정 > 현재 코드에서 확인한 구현 상태 > 최신 통합 문서 > 이전 구현 보고 순으로 차이를 해석한다. 코드가 의도와 다르면 어느 쪽도 조용히 덮어쓰지 말고 설명한다.
