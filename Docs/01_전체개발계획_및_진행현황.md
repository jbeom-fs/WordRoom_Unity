# WordRoom — 전체 개발 계획 및 진행 현황

작성·갱신일: **2026-10-23**  
현재 구현 기준: **Unity 커밋 `79a6ba2`**  
새 세션은 [프로젝트 인수인계](00_프로젝트_인수인계.md)를 먼저 읽는다.

이 문서는 지금까지 합의한 게임 기획, 구현 현황, 다음 단계와 미결정을 모은 기준 문서다. 앞으로 할 일을 이미 구현된 기능처럼 적지 않는다. 구현 상세는 기존 1·2단계 문서를 함께 사용한다.

## 챕터 1. 게임의 목적과 확정된 경험

### 1.1 핵심 목표 — 기획 확정 / 게임 전체 미구현

WordRoom은 단어의 연관성을 이용해 시작 단어에서 목표 단어로 이동하는 **2~4인 협동 탐색 게임**이다. 방 하나가 단어 하나를 나타낸다. 플레이어가 상·하·좌·우의 단어를 보고 이동 방향을 선택하면, 그 선택과 기존 지도 상태를 바탕으로 새로운 방의 단어가 생성된다.

목표 단어가 항상 같은 좌표에 있을 필요는 없다. 목표 방향으로 단어의 흐름을 유도하며 탐색하는 것이 핵심이다. 목표 유도 보정도 현재 규칙에 포함된다.

- 팀원 중 **한 명만 목표 방에 도착해도 팀 전체 성공**이다.
- 모든 플레이어는 서로 떨어져 원하는 방을 자유롭게 탐색할 수 있다.
- 목표는 항상 표시한다.
- 현재·목표 단어는 좌상단 HUD에, 연결된 다음 방 단어는 해당 방향 벽의 `WordTag/Word/WordText`에 표시한다. HUD는 `373de03`에서 구현·커밋됐다.
- 팀원이 발견한 방과 단어는 모두에게 공유한다.
- 별도의 단어 능력은 추후 검토이며 기본 범위에 넣지 않는다.

### 1.2 공간과 조작 — 단독 탐색·문·방 진입 구현

- 단순한 정사각형 방이 같은 높이에서 네 방향으로 확장된다. 위층·아래층은 없다.
- 1인칭 시점으로 직접 걸어간다.
- 문 앞에서 상호작용으로 문을 열고 직접 통과한다.
- 열린 문은 계속 열린 상태를 유지한다.
- 별도 입장 연출은 필요 없다.
- 플레이어끼리는 통과할 수 있다.
- 사용자에게 방향을 표기할 때는 상·하·좌·우를 사용한다.

아카이브 방 모델을 사용한다. 방 간격 6.2m, 출입구 폭 1.3m·높이 2.2m, 플레이어 높이 1.8m·시점 1.6m다. 화면 중앙 2m 안 문을 E로 열면 0.5초 동안 2.2m 상승한다. 목적지 방 주변은 문 열기 시 준비하고, 실제 경계 통과 시 이동·방문·목표 판정을 한 번 처리한다. 멀티플레이어 간 통과는 협동 단계 과제다.

### 1.3 세션 — 단독 시작 흐름 구현 / 협동·결과 일부 미정

- 일반 플레이는 시작·목표 단어를 사용자가 입력하지 않는다. 선택한 난이도의 빈도 범위 안에서 서로 다른 두 단어와 시드를 자동으로 뽑는다. 직접 입력은 개발용 Inspector에만 남긴다. 기존 직접 입력 지원 계획은 이 결정으로 대체한다.
- 메인 메뉴는 시작·설정·종료. 시작 후 쉬움(상위 5,000개)·보통(10,000개)·어려움(15,000개)을 선택한다. 단어 수 기준이며 글자 수 기준이 아니다. 길이 범위는 모두 1~8글자다.
- MainMenu → Gameplay 진입과 Esc 메뉴(계속·설정·메인 메뉴·종료)를 구현했다. 메인 복귀 시 세션을 폐기한다.
- 진행 중 신규 참가 불가. 재접속은 신규 참가와 별도로 취급한다.
- 재접속자는 이전 위치로 돌아온다. 이탈 중 캐릭터는 숨긴다.
- 재접속 허용 시간은 **5분을 희망**하지만 Photon 환경의 지원과 상태 유지 정책 확인 후 확정한다.
- 성공 후 대기실로 돌아간다. 결과는 소요 시간과 방문 방 수를 표시한다.
- 도착한 플레이어 이름을 결과에 표시할지는 보류다.
- 모두 나가면 세션을 종료한다. 영구 저장 기능은 없다.
- PC 우선, Android는 여건에 따라 후속 검토한다.

## 챕터 3. 데이터 이식 — 완료

### 3.1 입력과 산출물

Python 1.1.0의 활성 어휘 `v2_15000`을 Unity용 패키지로 내보냈다.

| 항목 | 수량·위치 |
|---|---|
| 표기 / 뜻 | 15,000개 / 48,318개 |
| E5 / fastText | 뜻별 768차원 / 표기별 300차원 |
| 호환 관계 판정 | 82,921행 |
| 패키지 | `Assets/StreamingAssets/WordRoomData/` |
| 도구 | `Tools/DataExport/` |
| 데이터 조회 | `WordRoom.Data` |
| 개발용 화면 | `Assets/WordRoom/Scenes/DataCheck.unity` |

단어·뜻·설정·관계 메타는 JSON, 벡터와 관계 레코드는 헤더가 붙은 바이너리로 관리한다. 표기 순위, 뜻 ID와 벡터 행의 대응을 보존한다. 단어 표기 전체와 뜻별 자료를 함께 유지한다.

관계는 YES만 담지 않는다. NO, 기준 미달, 불완전·오류 상태도 구별하고 미검사는 기록 없음으로 취급한다. 서로 다른 뜻 조합 중 적격 근거가 있으면 단어 관계로 집계하는 B 규칙을 따른다. B 규칙의 판정 방향 처리 역시 현재 데이터 규칙 `either-order-yes-v1` 및 원본 구현을 기준으로 한다.

### 3.2 해결한 문제: 데이터 교체 실패

기존에는 새 패키지 활성화 후 기준 파일을 복사해, 복사 실패 시 패키지와 기준값 버전이 어긋날 수 있었다. 오류 안내도 기존 상태가 유지됐다고 잘못 표시했다.

`wr_swap.py`로 패키지·기준값·보고서를 하나의 묶음으로 관리하도록 고쳤다. 준비 완료 → 기존 묶음 백업 → 교체 기록 → 항목별 교체 → 패키지 ID 확인 → 성공 확정 → 오래된 백업 정리 순서다.

실패 시 복구하고, 복구 실패 시 자료와 위치를 남긴다. 강제 종료 다음 실행의 복구 절차를 두고, 백업 정리 실패는 활성화 성공과 별도로 알린다. 실제 플레이의 관계 판정 DB를 수정하는 작업은 아니다.

### 3.3 확인 근거와 한계

기존 보고·기록상 Python 원본과 27개 항목 비교, EditMode 22개 테스트, PC 빌드 확인을 수행했다. 패키지 약 171.6 MiB, 해시 포함 로딩 약 3초, 관리 힙 증가 약 187MB였다. 이는 데이터 단계 측정이다.

현재 에이전트는 빌드·검증을 수행하지 않는다. 과거 검증 기록과 새 사용자 검증을 구분한다. Android 접근은 미지원이다.

## 챕터 4. 단어 방 생성 엔진 — 완료

### 4.1 데이터와 생성 규칙

- 데이터 패키지는 빈도 상위 15,000개 표기, 1~8글자 명사 중심이다. 일반 게임에서는 난이도별 5,000·10,000·15,000개 범위를 사용한다. 실제 목록은 기존 패키지를 사용한다.
- 동음이의어를 방마다 한 뜻으로 고정하지 않는다. 같은 표기의 여러 뜻을 통해 연결 방향을 바꿀 수 있다.
- 목표 도착은 **표기 일치**로 판정한다.
- 좌표 하나에는 단어 하나만 확정하고, 생성된 좌표의 단어를 다시 추첨하거나 바꾸지 않는다.
- 설정은 실험 시작 시 복사해 고정한다.

| 방향 | 논리 좌표 변화 |
|---|---|
| 상 | `(x, y+1)` |
| 하 | `(x, y-1)` |
| 좌 | `(x-1, y)` |
| 우 | `(x+1, y)` |

화면 출력 순서는 상·하·좌·우이고, 원본 재현을 위한 내부 생성 순회는 상·우·하·좌다. 출력 순서를 맞춘다고 내부 후보 처리 순서를 임의 변경하지 않는다.

### 4.2 생성 범위와 중복 규칙 — 확정

시작 `(0,0)`에서는 주변 최대 네 방을 생성한다. 이후 **문을 여는 시점에 목적지 방의 비어 있는 이웃을 Prepare로 생성**한다. 지나온 방은 이미 있으므로 보통 최대 세 방이며, 기존에 만들어진 방이 있으면 더 적다. 실제 입장은 Enter로 이동·방문·목표 판정만 한다. 방향키 디버그의 Move만 입장+Fill을 유지한다. 미방문 방의 주변을 재귀적으로 계속 생성하지 않는다. 표시 거리 설정도 생성 요청을 만들지 않는다.

중복 제한은 **후보가 배치될 좌표를 기준으로 맨해튼 거리 3 이하에서 같은 표기를 금지**한다. 거리 4 이상은 다른 조건을 만족하면 같은 표기가 다시 나올 수 있다.

- 초기 배치, 문 열기 시 주변 배치, 디버그 Move, DB 후보, fastText 보충에 동일하게 적용한다.
- 기존 확정 방뿐 아니라 이번에 함께 놓을 임시 후보끼리도 비교한다.
- “최대 세 방 생성”과 “중복 거리 3”은 다른 개념이다.
- 코드의 `RepeatRadius` 기본값이 3이며 DB·fastText에서 공통 참조한다.
- 엔진에는 중복 사용 여부·범위 설정도 남아 있지만, 확정된 일반 게임 규칙은 중복 금지 켬·주변 거리 3이다. 이를 변경하려면 별도 합의한다.

### 4.3 DB → fastText → 목표 유도

1. 비어 있는 주변 위치를 함께 계획한다.
2. 각 위치의 모든 인접 방과 관계가 성립하는 후보를 찾는다.
3. 백트래킹과 탐색 상한을 적용한다.
4. DB 기준을 기본 `0.8 → 0.7 → … → 0.1`로 완화한다.
5. 완성하지 못하면 fastText 보충을 적용한다.
6. 빈 위치 수, 약한 연결 수, fastText 연결 수, 유사도 등 기존 배치 품질 순서를 따른다.
7. 목표 유도는 배치의 절대 조건과 연결 품질 우선순위를 유지하면서 후보 순위에 반영한다.

fastText 선호 하한 기본값은 0.2이며 절대 금지선은 아니다. 제한 표기·NO 판정·낮은 유사도는 약한 연결로 취급하고, 다른 방법이 없는 경우 최후 수단으로 사용할 수 있다. 근거와 이유를 남기며 판정 DB에 새 YES를 써 넣지 않는다.

목표 유도 기본값은 켬, 고유 방문 방 10개까지 강도 0, 이후 40개에 걸쳐 최대 0.03이다. 시작 방도 고유 방문에 포함하고 재방문은 증가시키지 않는다. 유도 끔 설정도 유지한다. 유도 켬에서는 목표에 따라 생성 지도가 달라질 수 있다.

### 4.4 출입과 생성 실패

4방향 확보가 의도한 경험이다. 다만 현재 엔진은 유한 어휘·중복 조건·검색 상한 등으로 못 채운 위치를 표현할 수 있다. “무한히 탐색하도록 설계”와 “모든 상황에서 수학적으로 무한 생성 보장”은 다르다.

- 주변 준비 요청이 처리된 기존 인접 방은 일부 미생성을 이유로 출입을 막지 않는다. 준비 요청 자체가 완료되지 않은 목적지의 통과는 차단한다.
- 미생성 좌표로 이동하지 않는다.
- 문 열기 Prepare는 현재 위치·이동·방문·성공 상태를 바꾸지 않는다. 준비 거절·표시 실패·예외는 오류 정지하며 자동 재시도하지 않는다.
- 실제 Enter로 확정된 이동·목표 성공을 이후 표시 실패 때문에 되돌리지 않는다.
- 목표 방 주변도 문 열기 때 준비한다. 문을 연 것만으로 목표 성공이 되지 않으며 실제 입장이 필요하다. 디버그 Move는 기존처럼 입장 후 Fill과 목표 성공을 유지한다.
- 미생성과 원인을 기록한다. 같은 지도 상태에서 같은 실패를 계속 재시도하지 않는다.
- 인접 방 자체가 없는 상태는 `no_exit`이며, 이동 횟수 제한과 구분한다.

### 4.5 현재 확인 방법

`RoomGenerationDebug`의 Inspector에서 입력을 설정하고 사용자가 Play한다. 방향키 한 번에 한 칸 이동하며, 로딩·생성 중 입력은 버리고 큐에 쌓지 않는다. 현재 방과 상·하·좌·우 단어가 Debug.Log로 출력된다.

이는 개발용 생성 로직 확인 수단이다. Player가 활성이면 방향키 논리 이동을 차단한다. 실행 중 해제·교체 시 이전 플레이어 정지·커서 해제를 추가했고, 재배치는 새 실험에서만 한다. 일반 플레이는 MainMenu에서 시작한다. 자동 플레이어·자동 탐색·결과 JSON 통계는 현재 이식 범위 밖이다.

### 4.6 재현성과 남은 정밀도 차이

전용 난수, 좌표 시드, 원본 후보 정렬을 이식했다. `UnityEngine.Random` 전역 상태를 사용하지 않는다. NumPy와 C#의 내적·반올림·지수 계산 차이로 극소 차이 후보의 순서가 달라질 수 있어, 같은 시드의 Python 지도와 완전히 같다고 보장하지 않는다.

문 열기 때 생성하도록 시점이 바뀌어 입장 후보다 이동·방문 진행도가 한 번 적게 반영될 수 있다. 문을 연 순서도 생성 순서에 영향을 준다. 이전 버전과 같은 지도를 보장하지 않는다.

상세: [방 생성 이식 2단계](WordRoom_방생성이식_2단계.md).

## 챕터 5. 일반 플레이와 테스트 제한 분리 — 완료

일반 플레이에는 이동 횟수 제한이 없다. 자동 실험의 300회 상한을 게임 종료 규칙으로 가져오지 않기로 확정했다.

- `UseMoveLimit=false`가 기본이다.
- 테스트에서만 켜고 `MaxMoves`를 사용한다. 테스트 기본값은 300이다.
- 패키지의 `max_moves=300`은 횟수 값일 뿐 제한을 켜지 않는다.
- 제한 켬일 때만 최대 횟수 1 이상을 요구한다.
- 누적 이동은 제한 여부와 관계없이 기록한다.
- 목표 도착과 제한이 같은 이동에 겹치면 목표 성공이 우선이다.
- 마지막 허용 이동도 확정한다. 디버그 Move는 주변 Fill 후 종료 상태를 출력하고, 실제 플레이 Enter는 문 열기 때 이미 준비한 주변을 다시 생성하지 않는다.
- 미생성 방향 입력은 이동 횟수에 포함하지 않는다.
- Inspector를 바꿔도 새 실험부터 적용한다.

사용자가 검증·커밋 완료를 통보했다. 현재 커밋 `84f8863`에 반영됐다. 중복 규칙이나 생성 알고리즘 변경을 이 작업에 섞지 않았다.

## 챕터 6. 3D 방·공유 문·풀링·아카이브 모델 — 구현·커밋

### 6.1 기본 표현 계층

이미 생성된 논리 지도를 읽어 방과 문을 표시한다. 방·문은 각각 별도 풀을 사용하며, 필요한 기존 인스턴스를 유지하고 표시 범위를 벗어난 것만 반환한다. 반환해도 논리 지도와 연결별 문 상태는 남는다. 새 세션에서 초기화한다.

공유 연결당 문 하나이며 좌우는 왼쪽 방의 우 출입구, 상하는 아래쪽 방의 상 출입구를 기준으로 둔다. 미생성·숨겨진 방 방향에도 출입 차단을 유지한다. 사용자 루트 소유권 보호와 프리팹 설정 고정은 기존 구현을 유지한다.

기본 3D·루트 보호는 `ead01bc`, `770e6ab`에서 사용자 확인 완료다. [3단계 문서](WordRoom_3D방표시_3단계.md)는 당시 구현 상세이며 아래 후속 변경을 우선한다.

### 6.2 현재 표시 범위

- 맨해튼 거리 반경 1·2·3칸, 최대 5·13·25개의 **기존 방만** 표시한다. 기본은 1칸이다.
- 스냅샷은 현재 방부터 거리순, 상→하·좌→우 순으로 수집한다.
- RoomViewSnapshot과 RoomWorldView 양쪽의 기존 최대 5개 제한을 함께 변경했다.
- 반경 변경은 작업 스레드의 스냅샷 재캡처와 Show만 수행한다. Fill·Prepare·Move·Enter를 호출하지 않는다.
- 요청이 진행 중이면 종료 후 최신 반경을 반영한다. 중간 설정값마다 요청을 쌓지 않는다.
- 현재 방을 항상 포함한다. 표시 거리와 중복 금지 거리 3은 별개다.
- 갱신 중 이동 잠금 누락에 따른 입장 판정 위험은 KI-003으로 기록했다.

## 챕터 7. 1인칭 이동·문·실제 방 진입 — 구현·커밋

### 7.1 플레이어와 문 상호작용

- CharacterController 높이 1.8m·반지름 0.3m, 시점 높이 1.6m, WASD 3m/s, 수직 시점 제한 ±85°다.
- 화면 중앙 2m Ray로 첫 유효 물체가 열 수 있는 문일 때만 [E] 문 열기를 표시한다. 자기 Collider·Trigger·Ignore Raycast는 건너뛴다.
- E 수락 시 문 본체가 0.5초 동안 2.2m 상승하고 연결 상태를 Open으로 저장한다. 문 열기 자체로 이동·방문 수는 바뀌지 않는다.
- 본체 Collider는 완전히 올라간 뒤 끈다. 별도 PassageBlock은 완전 열림·현재 방 연결·표시된 목적지·준비 완료를 모두 만족해야 해제한다.
- 재표시된 열린 연결은 즉시 열린 위치로 복원한다. 풀 재사용 시 이전 애니메이션·차단 상태가 새 연결에 남지 않게 초기화한다.
- 생성 요청 중 걷기·E를 잠그되 시점·중력·Esc를 유지한다. 문 여는 중·주변 방 준비 중 자막은 사용하지 않는다.

### 7.2 이전 검토 문제의 처리

10월 21일 발견한 실행 중 Player 연결 해제·비활성 플레이어 배치 문제는 후속 구현에서 보완됐다. ActivePlayer로 활성 기준을 통일하고 TrackPlayer가 해제·교체·비활성화를 감지해 이전 제어를 해제한다. 다시 배치하려면 새 실험이 필요하다. OnDisable에서 배치 상태를 해제하며 비활성 PlaceAt을 거부한다.

카메라 기준 로컬 위치는 최초 한 번 기억하거나 직렬화한 값을 사용한다. 디버그 카메라가 이동한 위치로 기준을 덮어쓰지 않는다. Show는 실제 방·문·차단 인스턴스의 사용 가능 여부를 반환하며, 표시 실패를 시작 실패·Halt로 전달한다. 오류 시 이동을 되돌리거나 자동 재시도하지 않는다.

남은 취소 확인 문제 KI-001은 이 두 전환 문제와 별개다. 사용자 결정으로 낮은 우선순위의 기록만 유지한다.

### 7.3 문 열기 준비와 실제 입장 분리 (`60d4d3d`)

1. E로 문 열기 수락 → 상승 시작 → 같은 프레임 Prepare 요청.
2. 작업 스레드에서 목적지의 주변 Fill과 스냅샷 캡처. 현재 좌표·이동·방문·성공 상태는 유지한다.
3. 현재 방 중심으로 Show. 목적지 준비와 문 상승이 모두 끝나면 통과를 허용한다.
4. LateUpdate에서 직전 위치와 현재 위치의 구간이 경계 밖 0.15m 지점을 출입구 폭 안으로 넘었는지 판정한다.
5. Enter는 준비된 이웃으로 Map.Enter와 목표·테스트 이동 제한 판정만 한다. Fill은 호출하지 않는다.
6. 목적지 중심 Show와 도착 바닥 확인 후 기존 위치·시점에서 이동을 재개하고 HUD 현재 단어를 갱신한다.

Fill 요청 처리 기록은 네 방향 완성 여부와 다르다. 일부 미생성과 skipped_same_state도 준비 처리됨으로 보되, 미생성 방향의 문은 열 수 없다. 이미 준비된 방을 다른 닫힌 문으로 열면 기존 엔진 재시도 정책에 따라 요청을 처리할 수 있다. 새 판에서 준비 기록·문 상태를 초기화한다.

방향키 디버그 Move는 입장+Fill을 유지한다. 사용자가 생성/입장 분리 기능의 검증 완료를 통보했다. 모든 취소·지연·교체 경로가 검증됐다고 확대하지 않는다.

## 챕터 8. 단독 게임 흐름·HUD·메뉴·설정 — 구현·커밋 / 결과·성능 미완료

### 8.1 시작 씬과 난이도 (`79a6ba2`)

MainMenu는 정적 아카이브 배경과 시작·설정·종료를 제공하며 생성 엔진·데이터 로드를 실행하지 않는다. 시작에서 난이도를 고른 뒤 Gameplay로 이동한다. 두 씬과 빌드 목록은 이미 존재한다. 개발용 RoomGenerationDebug 씬은 보존했다.

GameplayBootstrap은 Awake에서 Inspector 자동 시작을 끄고 시작 요청을 한 번 소비한다. 데이터 준비 후 CreateScope(limit, 1, 8).Ranks에서 서로 다른 시작·목표와 시드를 한 번 뽑는다. 보통이 기본이며 메뉴 없이 Gameplay를 직접 열어도 보통으로 시작한다. 후보 부족·시작 오류는 정지 안내로 처리하며 임의 재추첨하지 않는다. 일반 플레이 이동 제한은 끈다.

성공한 데이터셋은 패키지 경로·해시 옵션이 같으면 실행 중 재사용한다. 첫 표시·배치 완료 전에는 플레이어를 움직이거나 떨어뜨리지 않는다.

### 8.2 아카이브 HUD (`373de03`)

좌상단 320×96 패널, 기준 해상도 1920×1080에서 여백 32다. 짙은 목재 #49352A·황동 #A8874B·아이보리 계열로 현재·목표 두 줄만 표시한다. 입력을 받지 않는다.

현재·목표 문자열은 작업 스레드 스냅샷으로 전달한다. 문 열기·준비 중에는 유지하고 실제 입장 표시와 바닥 확인 후 현재 단어만 바꾼다. 목표는 세션 시작 값이다. 목표 도달 시 HUD는 유지하고 PlayHint가 종료 안내를 맡는다. 새 판·실패·플레이어 해제 등에서는 기존 단어를 숨긴다. 방향키 디버그는 HUD를 표시하지 않는다.

| 마우스 감도 / Y축 반전 | 0.2~3.0배, 기본 1 / 기본 꺼짐 |
| 수직 시야각 | 60~90도, 기본 60 |
| UI 크기 | 80~125%, 기본 100. 메뉴·HUD·PlayHint 공통 |
| 전체 / 효과음 음량 | 0~100%, 기본 각 100 |
| 화면 | 전체 화면·창 모드, 플랫폼 해상도 목록, 기본 전체 화면·디스플레이 크기 |

WordRoom.Settings. 접두사 PlayerPrefs만 사용한다. 범위를 보정하고 기본값 복원 시 다른 키·세션·난이도를 지우지 않는다. 화면은 적용 후 15초 동안 유지 확인을 받고, 취소·시간 초과·패널 닫기·씬 전환 시 직전 화면으로 복원한다. 첫 미확정 변경 후 앱 종료·재실행은 KI-002의 보완 대상이다. 창 모드 목록 제한 예외는 KI-005에 기록했다.

UI 크기는 CanvasScaler 기준 해상도를 배율로 나눠 적용한다. 끌기 중에는 놓을 때 적용하려는 구조지만 최초 트랙 누름 순서 문제 KI-004가 남아 있다. 월드 표지판은 UI 크기의 영향을 받지 않는다.

Esc 메뉴는 계속·설정·메인 메뉴·종료를 제공한다. 메뉴용 입력 차단은 시점·걷기·E·클릭 잠금을 막고 중력은 유지한다. 생성 중 이동 잠금과 별개라 메뉴를 닫아도 생성 잠금을 풀지 않는다. 닫는 입력의 게임 전달을 막기 위해 다음 프레임부터 조작을 허용한다. Time.timeScale은 멈추지 않는다.

UiSound는 코드로 만든 짧은 클릭음을 사용한다. 효과음 배율은 재생 시 한 번, 전체 음량은 AudioListener에 한 번 적용한다. 외부 음원·문 효과음·배경 음악은 추가하지 않았다.

메뉴·HUD·모델은 커밋됐지만 항목별 사용자 검증 완료 통보를 임의로 추가하지 않는다. HUD 컴포넌트를 비활성화해도 호출 측이 Show를 계속 호출해 UI를 다시 만들 수 있는 문제는 KI-008이다. 최신 메뉴 검토 4건, 이전 도구·HUD 검토 사항, 기존 KI-001은 [Known Issues](02_Known_Issues.md)를 따른다.

### 8.4 남은 결과·성능 작업

- 소요 시간과 방문 방 수를 표시하는 결과 화면, 성공 후 복귀 흐름.
- 시간 측정 시작·끝, 방문 방 집계 기준, 결과 화면 체류 방식 확정.
- 장시간 무제한 탐색에서 지도·경로·캐시 메모리 증가와 생성 지연 측정.
- 25개 표시·조명·시야, 좌표 증가 시 원점 이동 필요성 판단.
- 팀 결과 방문 수를 고유 방문 합집합으로 할지 등의 협동 집계 기준은 별도 결정.

## 챕터 9. Photon 협동 — 게임 기능 미구현

### 9.1 합의된 방향

호스트가 단어 생성의 최종 결정을 관리한다. 클라이언트는 이동·주변 생성 필요를 요청하고, 호스트가 기존 지도 또는 새로 확정한 결과를 전달한다. 클라이언트마다 따로 생성 결과를 추측해 지도를 확정하지 않는다.

호스트 생성 → 결과 전파 구조는 RPC 등으로 구현할 계획이지만 메시지 형식과 기술은 아직 설계 전이다. 현재 프로젝트에는 **PUN 2.56**이 설치돼 있다. Fusion용 API를 그대로 구현 지시하지 않는다.

### 9.2 구현 전에 필요한 상태 분리

현재 엔진의 `RoomMap.Position`, `Moves`, `Path`는 한 플레이어 기준이다. 따라서 네트워크 전달 코드만 추가하면 자유 분산 탐색이 완성되는 상태가 아니다.

멀티 단계에서는 다음을 분리한다.

- 공유 월드: 좌표별 단어·연결 근거·생성 기록·공유 방문 상태·문 상태.
- 플레이어별 상태: 위치, 개인 방문·이동, 연결 여부.
- 세션 상태: 목표, 설정, 시드, 패키지 버전, 성공·시간.

팀원이 동시에 같은 좌표를 요청해도 한 번만 생성·확정한다. 서로 다른 위치의 요청도 호스트가 처리 순서를 확정해 전파한다. 고유 방문 수에 따른 목표 유도 진행도를 팀 기준으로 집계할지, 다른 기준을 쓸지는 구현 전에 합의해야 한다. 최근 단어 이력 등 생성에 영향을 주는 상태의 공유 범위도 정의한다.

### 9.3 필요한 구현

- 2~4인 대기실, 준비·시작, 시작 후 신규 참가 차단.
- 플레이어 위치 동기화, 서로 통과.
- 생성/이동 요청의 유효성 검사, 중복 요청 처리.
- 확정 지도·방문·문·목표 성공 결과 전파.
- 동일 데이터 패키지 여부 확인 또는 명시적 ID 매핑.
- 차이 반영 메시지와 전체 상태 복구 방식 분리.
- 한 플레이어 도착으로 세션 전체 성공을 한 번만 확정.

전체 벡터나 관계 DB를 RPC로 매번 전달하지 않는다. 실제로 전송할 간결한 데이터 형식은 별도 설계한다. `GenerationUpdate` 전체 객체를 그대로 Photon에서 전송할 수 있다고 가정하지 않는다.

## 챕터 10. 재접속·호스트 인계 — 상세 설계 전

확정된 방향은 이탈 캐릭터 숨김, 재접속 시 이전 위치 복귀, 호스트 이탈 시 다른 참가자가 역할을 이어받는 것이다. 기존 호스트가 돌아와도 자동으로 권한을 되찾지 않고 일반 플레이어로 복귀한다.

재접속 5분은 희망값이며 제품·설정 확인이 필요하다. 전원 퇴장 시 종료와 재접속 대기의 경계도 정의해야 한다. 영구 세이브가 없더라도 세션 동안 복구 자료를 유지해야 한다.

보관·복구 대상: 확정 지도, 문 상태, 플레이어별 위치, 방문, 목표 유도에 쓰는 이력, 설정·시드·패키지 식별, 성공/시간, 그림 상태, 처리된 요청 순서 등. 논리 지도만 복사하고 생성에 영향을 주는 이력을 누락하면 인계 뒤 생성이 달라질 수 있다.

호스트 역할 변경 자체와 게임 상태 인계 완료는 다르다. Photon 기능만으로 사용자 정의 데이터가 자동 복구된다고 가정하지 않는다. 관련 API·제약 확인은 해당 구현 단계에서 공식 문서와 현재 설치 제품을 기준으로 진행한다.

## 챕터 11. 공유 지도·그림 — 기획 확정 / 미구현

### 11.1 지도

- 팀이 발견한 방문 방과 미방문 방을 구분.
- 방 단어와 플레이어 위치 표시.
- 확대·이동 지원.
- 아직 생성되지 않은 전체 맵을 공개하는 방식이 아님.
- 핑은 보류.

### 11.2 공유 그림

- 모든 팀원에게 그림 공유.
- 플레이어별 색상 구분.
- 본인 그림만 삭제 가능.
- 새 판에서는 초기화.
- 화면 픽셀 위치가 아니라 지도 좌표에 연결해 확대·이동해도 같은 장소에 남고 함께 확대됨.

필요 설계: 선/획 ID, 작성자, 지도 좌표점, 삭제 권한, 재접속 시 전달, 데이터 증가 제한. 선 굵기·색상 배정·지우개 UX·전송 주기는 아직 미정이다.

## 챕터 12. 통합과 후속 작업 — 미착수

각 단계의 빌드·검증은 사용자가 직접 수행한다. 에이전트는 코드 검토, 변경 내역, 확인 절차와 기대 결과를 제공한다.

통합 확인 대상은 장시간 탐색, 분산된 여러 플레이어, 동시 생성 요청, 한 명의 목표 도착, 재접속, 호스트 인계, 새 판 초기화, 그림 작성자별 삭제, 패키지 불일치 등이다. 현재 이를 통과했다고 기록하지 않는다.

후순위:

- Android 파일 접근·입력·메모리·기기 검증.
- 핑과 별도 단어 능력.
- Photon 데모 에셋 정리 — 실제 참조 확인 전 삭제하지 않음.
- 데이터 로딩 최적화 — 약 3초라는 과거 수치만으로 해시 검사를 제거하지 않고 필요 시 검토.
- 관계 DB 추가 준비·어휘 품질 개선 — 현재 Unity 이식 작업과 분리하고 별도 승인 범위로 진행.
