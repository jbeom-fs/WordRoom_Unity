# WordRoom 3단계 — 3D 방·공유 문 배치와 오브젝트 풀링

> 상태: **코드 구현 / 사용자 검증 대기.** Unity 실행·컴파일·빌드·테스트·자동 검증은 하지 않았습니다. 아래 수치와 배치 계산은 프리팹 파일(YAML)을 읽어 계산한 값이며, 화면에서 확인한 결과가 아닙니다.
>
> 2026-10-20 추가: 실험 시작 시 설정 고정과 Room/Door Root 변경 처리를 고쳤습니다(9.1절). 상태: **수정 코드 작성 / 사용자 검증 대기.**

기존 단어 생성 엔진(`WordRoom.Generation`)은 바꾸지 않았습니다. 생성된 논리 지도를 읽어 3D로 보여 주는 표현 계층(`WordRoom.World`)을 추가했습니다. 단어 패널·3D 텍스트·1인칭·문 열기 상호작용·문 애니메이션·Photon·지도 UI는 이번 범위가 아닙니다. 단어 확인은 기존 Debug.Log를 그대로 씁니다.

`WordRoom.World`는 `WordRoom.Generation`만 참조합니다. 생성 엔진은 GameObject·MonoBehaviour·Photon에 의존하지 않는 상태 그대로입니다.

## 2. 엔진과 표현의 연결

1. 새 실험: `RoomGenerationDebug.StartExperiment` → `RoomWorldView.BeginSession()` — 표시 중인 방·문을 풀에 반환(인스턴스는 재사용 대기), 이전 세션의 문 상태 삭제, 배치 설정 고정.
2. `RoomGenerator.Start`/`Move`는 기존처럼 작업 스레드에서 실행합니다. **요청이 끝난 직후 같은 작업 스레드에서** `RoomViewSnapshot.Capture(map)`으로 현재 방과 상·하·좌·우 중 **RoomMap에 있는 방만** 복사합니다. 메인 스레드는 생성 중인 RoomMap을 순회하지 않습니다.
3. 메인 스레드로 돌아와 기존 Debug.Log를 출력한 뒤 `RoomWorldView.Show(snapshot)`을 호출합니다.
4. 미생성 방향 입력은 기존처럼 거절되고(이동 횟수 증가 없음) 표시도 갱신하지 않습니다. 목표 도착·이동 제한 종료 이동도 이동 결과이므로 최종 배치가 반영됩니다.
5. 이전 실험의 늦은 결과는 기존 토큰·`gen != generator` 검사로 버려져 새 실험 표시에 섞이지 않습니다.

표현 계층은 `RoomGenerator.Start/Move/Fill`을 호출하지 않고, 단어를 만들거나 바꾸지 않습니다. 재방문 시 표시되는 방은 RoomMap에 저장된 단어의 좌표입니다. 시드·후보·목표 유도·중복 규칙은 표시 범위나 카메라와 무관합니다.

`RoomWorldView`가 없거나 설정이 빠져 있으면 오류를 한 번 출력하고 3D 표시만 건너뜁니다. 단어 생성과 Console 디버그는 계속됩니다. 표시 갱신 중 예외도 생성을 멈추지 않습니다.

## 3. 표시 범위와 차이 반영

- 활성 방 = 현재 좌표 + 상·하·좌·우 중 생성된 좌표 → **최대 5개**. 주변 방의 주변은 활성화하지 않습니다.
- 미생성 좌표에는 방을 만들지 않습니다(빈 방으로 이동 가능해 보이지 않게).
- 활성 문 = 활성 방마다 네 출입구의 연결 ID를 모아 중복 제거한 집합. 최대 16개(현재 방 4 + 이웃 방마다 바깥 3).
- 갱신 순서: 원하는 방·문 집합 계산 → 더 이상 필요 없는 방·문 **먼저 반환** → 없는 것만 대여. 계속 필요한 인스턴스는 그대로 둡니다.
- 풀에는 용량 상한이 없습니다. 5개 제한은 표시 집합으로만 관리합니다.

## 4. 좌표와 배치

- 논리 `(x, y)` → 월드 `worldOrigin + (x × 간격, 0, y × 간격)`. 상 +Z, 하 -Z, 좌 -X, 우 +X.
- 간격: `Room Spacing`이 0 이하(기본)면 **방 프리팹 메시 전체 크기**(가로·세로 중 큰 값)로 자동. TestRoomPrefab은 바닥 5.2 × 5.2라 5.2가 됩니다. 5.2를 코드에 적어 두지 않았습니다.
- 방 인스턴스는 대여할 때마다 위치·회전(프리팹 루트 회전)·스케일(프리팹 루트 스케일)을 명시적으로 지정합니다. 누적 변형이 없습니다.

### TestRoomPrefab 파일 구조 검토 (YAML에서 계산)

| 항목 | 값 |
|---|---|
| 바닥 | 5.2 × 5.2, 두께 0.1 (윗면 y 0.05) |
| 벽 | 바닥 안쪽 가장자리에 두께 0.1(예: 우 벽 x 2.5~2.6), 높이 2.8 (윗면 y 2.85) |
| 출입구 | 폭 1 (벽 중앙 -0.5~0.5), 높이 1.5 (y 0.05~1.55), 위는 인방 벽 |
| DoorPoint | 네 개 모두 **벽 바깥면의 출입구 한쪽 모서리**, 높이 0.05. 상 (-0.5, 0.05, 2.6), 하 (0.5, 0.05, -2.6), 좌 (-2.6, 0.05, -0.5), 우 (2.6, 0.05, 0.5) |
| DoorPoint 회전 | 부모 벽 회전과 상쇄되어 네 개 모두 방 기준 회전 없음 → 회전 복사로는 좌 출입구 문이 빗나감 |

간격 5.2로 놓으면 이웃 두 방의 벽이 등을 맞댄 **0.2 두께 이중 벽**이 됩니다. 두 벽은 x = 2.6 같은 면에서 맞닿지만 서로 겹치지 않고, 맞닿은 면은 벽 사이에 숨어 보이지 않을 것으로 예상합니다(화면 확인 필요). 출입구는 0.2 깊이 통로가 되고, 두 방의 출입구 위치는 서로 일치합니다. **프리팹 편집은 필요하지 않다고 판단했습니다.**

## 5. DoorPoint와 문 방향·위치

- DoorPoint는 이름만으로 하나를 찾지 않습니다. `Door Point Name`(기본 `DoorPoint`)인 오브젝트를 모두 찾아 **부모 벽 변환까지 포함한 방 기준 위치**로 분류합니다(|x| > |z|면 좌/우, 아니면 상/하). 결과는 실험 시작 시 한 번 계산해 고정하고, 매 프레임 검색하지 않습니다.
- 방향 누락·중복·대각선 위치는 “상: 없음 / 우: 2개 중복(경로·위치)”처럼 알려 주고 3D 표시를 멈춥니다. 이때는 `Door Point Overrides`에 네 방향을 직접 지정할 수 있습니다.
- TestDoor: 부모 피벗이 문 본체의 한 모서리이고, 본체 `Door`는 두께 0.1(X)·폭 1(-Z)·높이 1.5, 중심 (0.05, 0.75, -0.5).
- 회전 결정: TestDoor 부모를 Y축으로만 돌립니다. 본체의 얇은 축이 출입구 바깥 방향과 평행한 두 각도 중, **본체가 DoorPoint 모서리에서 출입구 가운데 쪽으로 뻗는 각도**를 고릅니다. DoorPoint 회전은 쓰지 않습니다.
- 계산 결과(프리팹 수치 기준): 우 출입구 Y 0°, 상 출입구 Y 270°. 닫힌 본체는 출입구 1 × 1.5를 그대로 덮고, 두께 0.1은 기준 방 벽의 **바깥쪽**(= 이웃 방 벽 두께 위치)에 놓입니다.
- 보정값 `Door Offset`(기본 0): x = 벽 바깥(+)/방 안쪽(-), y = 위, z = 출입구 가운데 방향. 예를 들어 x = -0.05이면 문이 두 벽의 경계에 걸치고, x = -0.1이면 기준 방 자신의 벽 구멍에 들어갑니다.
- 실험 시작 시 Console에 방향별 DoorPoint, 문 회전, 문 위치, 닫힌 본체 중심이 출력됩니다.

## 6. 공유 문

- 연결 ID: 두 좌표를 (x, 그다음 y) 순으로 정렬한 쌍. 좌우 연결은 왼쪽 좌표, 상하 연결은 아래쪽 좌표가 기준(A)입니다.
- 배치 기준: 좌우 = 왼쪽 방의 **우** 출입구, 상하 = 아래쪽 방의 **상** 출입구. 기준 방이 비활성이거나 미생성이어도 좌표와 프리팹 계산값만으로 위치를 구하며, 기준 방을 활성화하지 않습니다.
- 연결 ID마다 활성 문 인스턴스는 최대 하나(`Dictionary<RoomConnection, DoorView>`). 방문·요청 순서와 무관하게 같은 위치입니다.
- 문은 방의 자식이 아니라 별도 `Doors` 루트와 문 풀에서 관리합니다. 한쪽 방이 반환돼도 다른 활성 방이 필요로 하는 문은 남습니다.

## 7. 경계 문 (미생성·비활성 이웃)

- 활성 방의 네 출입구 모두에 문을 둡니다. 반대편이 비활성이든 미생성이든 **닫힌 문**이 경계를 막습니다.
- 문이 있다고 논리 방이나 이동 가능 연결이 생기지 않습니다. 이동 가능 여부는 계속 RoomMap이 결정합니다(방향키 이동 거절 그대로). 미생성 좌표의 단어를 만들지 않습니다.
- 문은 어떤 활성 방에서도 필요하지 않을 때만 반환합니다.

## 8. 풀과 문 상태

- 방 풀·문 풀이 따로 있습니다. 대여 중 목록으로 같은 인스턴스의 중복 대여·중복 반환을 막고, 반환 시 활성 목록에서 제거한 뒤 비활성화합니다.
- `DoorView`는 인스턴스 생성 직후 본체의 **원래 닫힘 로컬 위치**와 Collider 활성 값을 저장하고, 대여·반환 때마다 이 값으로 되돌립니다. 이전 연결의 열림 위치나 Collider 상태가 남지 않습니다.
- `DoorView.Apply(state)`는 본체 위치와 Collider를 함께 즉시 반영합니다(열림 = 닫힘 위치 + 위로 `Door Open Lift`, Collider 끔). 저장된 열린 연결을 다시 표시할 때 애니메이션 없이 바로 열린 상태가 됩니다.
- `RoomWorldView.SetDoorState(id, state)`가 다음 단계의 경계입니다. 현재는 이를 호출하는 입력이 없어 **모든 문은 닫힌 상태**입니다. 문 상호작용은 구현되지 않았습니다.
- 반환 시 정리할 이벤트 구독·비동기 작업은 현재 없습니다(바인딩·이름·상태만 초기화).

## 9. 새 실험·재방문·종료

| 상황 | 처리 |
|---|---|
| 표시 범위에서 벗어남 | 인스턴스만 풀로 반환. RoomMap 단어·문 상태 유지 |
| 재방문 | RoomMap의 같은 단어 좌표로 다시 대여. 문은 저장 상태 적용 |
| 새 실험 | 모든 활성 방·문 반환 + 문 상태 초기화. 풀 인스턴스는 재사용. 프리팹·이름·보정값이 바뀌었거나 루트가 바뀐 풀만 비우고 다시 구성(9.1절) |
| 오브젝트 파괴·Play 종료 | 풀이 만든 활성·대기 인스턴스만 Destroy, 목록·문 상태 정리, 사용하지 않는 자동 루트 정리 |

RoomMap은 표현 계층이 지우지 않습니다. 새 지도는 새 `RoomGenerator`가 만듭니다.

### 9.1 실험 시작 시 고정되는 설정과 루트 처리 (수정 코드 작성 / 사용자 검증 대기)

`BeginSession()` 순서: **기존 표시 반환·문 상태 초기화 → 프리팹 설정 확정 → 루트 확보 → 필요한 풀만 재구성 → 배치 값 고정** → 이후 생성 결과가 오면 새 지도 표시.

| 고정되는 것 | 출처(실험 중 이것만 사용) |
|---|---|
| 방·문 프리팹, 문 본체 이름(Door Body Name), DoorPoint 분류·지정, Door Offset, 방향별 문 회전·위치 | `RoomPrefabLayout` — 설정이 바뀌었을 때만 다시 계산 |
| 방·문 인스턴스의 부모 루트 | 각 풀의 `Parent` — 풀을 만들 때 정해지고 풀이 살아 있는 동안 바뀌지 않음 |
| 간격·원점·열림 상승 거리 | 실험 시작 시 저장한 값 |

- 풀의 생성 콜백은 풀을 만들 때의 `RoomPrefabLayout`과 `Parent`만 받습니다. Inspector 필드를 다시 읽지 않습니다. 그래서 첫 생성 대기 중이나 실험 도중에 Door Body Name·프리팹·루트를 바꿔도 현재 실험의 새 인스턴스에는 섞이지 않습니다. 문 본체를 찾는 이름은 배치 계산에 쓴 이름과 항상 같습니다.
- 바뀐 Inspector 값은 **다음 새 실험**(`새 실험 시작` 또는 다시 Play)에서 적용됩니다. 대여·반환 중에는 설정을 다시 읽거나 루트를 검색하지 않습니다.
- 확인용 카메라 설정(Move Camera·Offset·Euler)은 배치에 영향이 없어 갱신 때마다 현재 값을 씁니다.

**루트 결정**

- Room Root·Door Root가 지정돼 있으면 그 장면 오브젝트를 씁니다.
- 비어 있으면 이 컴포넌트가 만든 자동 루트(`Rooms`/`Doors`, 이 오브젝트의 자식)를 씁니다. 자동 루트는 처음 한 번 만들고 이후 실험에서 재사용하며, Inspector 필드에는 써 넣지 않습니다. 자동 루트가 외부에서 파괴됐을 때만 새로 만듭니다.
- 자동 루트 생성은 프리팹 배치 정보를 다시 계산하는지와 상관없이 매 실험 시작 때 확인합니다. 루트가 null인 상태로 속성에 접근하지 않습니다.
- 지정한 루트가 파괴됐거나("Missing") 프리팹 자산이면 오류를 출력하고 그 실험은 3D 표시를 하지 않습니다. 다른 부모로 대신 배치하지 않습니다. 실험 도중 루트가 파괴되면 그 뒤 새 인스턴스 생성은 오류로 거절됩니다.

**루트 변경 반영 — 방식 B(해당 풀 정리 후 새 루트로 재구성)**

- 새 실험에서 확정한 루트가 풀의 `Parent`와 다르면, 그 풀(방 또는 문 각각)이 만든 인스턴스만 Destroy하고 새 루트로 새 풀을 만듭니다. 이전 루트와 새 루트에 인스턴스가 섞여 남지 않습니다.
- 루트가 같으면 기존 풀과 대기 인스턴스를 그대로 재사용합니다.
- B를 고른 이유:
  - 프리팹 변경 때 이미 쓰는 "풀 정리 → 재구성" 경로를 그대로 쓰므로 새 상태 조합이 생기지 않습니다.
  - 일부만 옮겨진 중간 상태나 파괴된 이전 루트 아래 인스턴스가 남을 여지가 없습니다.
  - 풀의 부모를 풀이 살아 있는 동안 바꾸지 않는다는 규칙 하나로 생성 콜백과 기존 인스턴스가 항상 같은 루트를 씁니다.
  - 비용은 루트를 바꾼 직후 실험에서 인스턴스를 다시 만드는 것뿐입니다. 루트 변경은 드문 설정 작업입니다.

**정리와 소유권**

- 풀은 자기가 만든 인스턴스만 Destroy합니다. 사용자가 지정한 루트 오브젝트와 그 아래의 다른 자식은 삭제하지 않습니다.
- 더 이상 쓰지 않는 자동 루트는 삭제합니다. 다만 풀 인스턴스가 아닌 오브젝트가 들어 있으면 삭제하지 않고 경고와 함께 남겨 두며, 더 이상 관리하지 않습니다. 사용자가 자동 루트를 Inspector 루트로 직접 지정하면 그 루트는 사용자 소유로 넘어가 삭제 대상에서 빠집니다.
- 정리 전에 활성 좌표·연결 목록을 비우고 풀의 대여·대기 목록도 비우므로 오래된 참조가 남지 않습니다.
- 설정 오류(프리팹 누락, DoorPoint 분류 실패, 루트 문제)는 3D 표시만 끕니다. 단어 생성과 Console 디버그는 계속됩니다. 설정을 고치고 새 실험을 시작하면 다시 준비합니다.

## 10. 확인용 카메라

`Move Camera`가 켜져 있고 `Debug Camera`가 지정된 경우에만, 표시 갱신 때 카메라를 `현재 방 중심 + Camera Offset`, 회전 `Camera Euler`로 옮깁니다. 기본값은 높이 16에서 아래를 보는 시점(화면 위쪽 = 상)으로, 5개 방이 한 화면에 들어오도록 정한 값입니다. 실제로 들어오는지는 시야각과 화면 비율에 따라 다르므로 확인이 필요합니다. 방 안 시점은 Offset (0, 1.6, 0), Euler (0, 0, 0)처럼 바꿀 수 있습니다.

카메라가 없어도 생성·표시는 동작합니다. 장면의 카메라·렌더링·조명·프로젝트 설정은 바꾸지 않습니다. 렌더 거리만으로 표시 범위 밖이 자연스럽게 가려지지는 않습니다. 위에서 보면 범위 밖은 비어 보입니다. 안개·어둠·최종 시야 연출은 후속 조정 항목입니다.

## 11. 사용자 설정

1. `RoomGenerationDebug` 장면을 엽니다.
2. 메뉴 **WordRoom → Room Debug → Add 3D Room View**를 실행합니다. 선택 오브젝트(없으면 장면의 `RoomGenerationDebug`)에 `RoomWorldView`를 추가하고 **비어 있는 칸만** 채웁니다.
   - `Room Prefab` ← `Assets/Prefabs/TestRoomPrefab.prefab`
   - `Door Prefab` ← `Assets/Prefabs/TestDoor.prefab`
   - `Debug Camera` ← `Camera.main`
   - `RoomGenerationDebug.World View` ← 추가한 `RoomWorldView`
3. 장면은 직접 저장합니다.

메뉴 대신 직접 연결해도 됩니다. 필수 항목은 `Room Prefab`, `Door Prefab` 두 개입니다. 나머지는 기본값을 쓸 수 있습니다.

| 항목 | 기본 | 설명 |
|---|---|---|
| Door Point Name | `DoorPoint` | 자동 분류 대상 이름 |
| Door Point Overrides | 비움 | 쓰려면 Project 창에서 방 프리팹을 펼쳐 네 DoorPoint를 모두 지정 |
| Door Body Name | `Door` | 위로 미끄러질 문 본체 자식 이름 |
| Door Offset | (0, 0, 0) | 5절 보정값 |
| Door Open Lift | 0 (= 본체 높이 1.5) | 열림 상태의 상승 거리 (현재 사용하는 입력 없음) |
| World Origin | (0, 0, 0) | 좌표 (0, 0) 방의 위치 |
| Room Spacing | 0 (= 자동) | 이웃 좌표 간 거리 |
| Room Root / Door Root | 비움 (= 자동 루트 생성·재사용) | 장면 오브젝트, 스케일 1 권장. 바꾸면 다음 새 실험부터 적용(9.1절) |
| Move Camera / Debug Camera / Camera Offset / Camera Euler | 켬 / 비움 / (0, 16, 0) / (90, 0, 0) | 확인용 카메라 |
| Verbose Pool Log | 끔 | 갱신마다 현재 좌표, 활성 방·문 목록과 개수, 대여·반환·새 생성 수, 풀 누적 |

장면에 Light가 없습니다(현재 `RoomGenerationDebug.unity` 기준). 방이 어둡게 보이면 Directional Light를 직접 추가하세요. 장면에 이미 놓여 있는 `TestDoor` 인스턴스(`GameObject` 아래)는 건드리지 않았습니다. 생성된 (0, 0) 방 근처에 겹쳐 보일 수 있습니다.

## 12. 사용자 확인 절차

준비: 11절 설정, `Verbose Pool Log` 켬, Play, Game 창 클릭 후 방향키.

목표 도착(`목표 도착`)과 테스트 이동 제한 종료(`실험 종료: 테스트 이동 제한 도달`)는 기존 종료 조건 그대로입니다. 3D 표시는 두 경우 모두 마지막 이동 결과를 반영할 뿐 종료 판정에 관여하지 않습니다.

| 확인 | 방법 | 기대 |
|---|---|---|
| 준비 로그 | Play | `[3D 방] 표시 준비` 아래 방 크기 5.2×5.2, 간격 5.2, 우 0°·상 270°, 닫힌 본체 중심 우 (2.65, 0.8, 0)·상 (0, 0.8, 2.65) 등 |
| 시작 배치 | 첫 출력 후 Scene/Game 창 | 시작 방 + 생성된 이웃 방(최대 5개). Console의 `미생성` 방향에는 방 없음. 활성 문 수 = 활성 방 출입구 연결 수 |
| 이동 갱신 | 방향키 이동 | 새 현재 좌표 기준으로 재배치. 로그 `이번 갱신`에서 범위를 벗어난 방만 반환, 새로 필요한 방만 대여 |
| 재방문 | 갔다가 되돌아오기 | Console의 단어가 이전과 같음. 같은 좌표에 같은 위치의 방 |
| 공유 문 중복 없음 | 이웃 방 사이 출입구 확인, 로그 문 목록 | 연결마다 문 하나(예: `(0, 0)-(1, 0)` 한 번만). Hierarchy `Doors` 아래 활성 문 중 같은 이름 없음 |
| 한쪽 방 반환 후 문 유지 | 상으로 이동 후 하 방향 경계 확인 | 현재 방과 이전 방 사이 문은 유지, 더 이상 어떤 활성 방에도 속하지 않는 문만 반환 |
| 풀 재사용 | 같은 구간을 여러 번 왕복 | `풀 누적`의 방·문 생성 수가 어느 시점부터 늘지 않고 대여·반환만 증가 |
| 미생성 방 | 미생성 방향 키 | 방 표시 변화 없음, 카메라 그대로. 미생성 좌표에 방 없음(닫힌 문만) |
| 새 세션 | 컴포넌트 메뉴 `새 실험 시작` (시드·단어 바꿔서) | 이전 방·문이 모두 반환된 뒤 새 지도만 표시. 이전 단어·문이 섞이지 않음 |
| 카메라·정렬 | Scene 창에서 확대 | 이웃 방 벽이 맞닿고 출입구 위치 일치, 닫힌 문이 출입구 구멍을 채움, 바닥 이음매 어긋남 없음 |
| 목표 도착 | 목표 방 진입 | Console `목표 도착` 유지, 3D는 목표 방 기준으로 마지막 갱신 |
| 3D 없이 | `RoomWorldView` 제거 또는 비활성 오브젝트 | 기존 Console 디버그만 정상 동작 |

### 12.1 설정 고정·루트 변경 확인 (9.1절 수정분)

| 확인 | 방법 | 기대 |
|---|---|---|
| 생성 대기 중 이름 변경 | 목표 근접도 계산 중(첫 출력 전)에 Door Body Name을 없는 이름(예: `X`)으로 바꿈 | 첫 표시의 문이 정상 생성됨(기존 `Door` 사용). 문 생성 오류 없음 |
| 다음 실험 반영 | 위 상태에서 `새 실험 시작` | 준비 단계에서 `'X' 자식(문 본체)이 없습니다` 오류, 이번 실험은 3D 표시 없음, Console 단어 출력은 계속 |
| 오류 후 복구 | 이름을 `Door`로 되돌리고 `새 실험 시작` | `표시 준비 … (프리팹 배치 정보 새로 계산)` 출력, 3D 표시 재개 |
| 루트 변경 | 장면에 빈 오브젝트 `MyRooms` 생성 → Room Root에 지정 → `새 실험 시작` | 방 인스턴스(활성·대기 모두)가 `MyRooms` 아래에만 있음. 자동 `Rooms` 아래 방 인스턴스 없음(자동 루트는 비어 있으면 삭제). 준비 로그 `루트: 방 'MyRooms'` |
| 진행 중 루트 변경 | 실험 도중 Room Root를 다른 오브젝트로 바꾸고 계속 이동 | 이번 실험의 새 방은 계속 이전 확정 루트 아래 생성. 다음 새 실험부터 새 루트 |
| 루트 비우기 | Room Root·Door Root를 비우고 `새 실험 시작` | 자동 `Rooms`·`Doors` 사용, null 오류 없음, 로그에 `(자동)` |
| 자동 루트 반복 | 같은 설정으로 `새 실험 시작` 여러 번 | Hierarchy의 `Rooms`·`Doors`가 하나씩만 유지, 대기 인스턴스 재사용(`풀 대기 인스턴스` 수 유지) |
| 사용자 루트 보존 | `MyRooms` 아래 다른 자식(예: `Note`)을 두고, Room Root를 비운 뒤 `새 실험 시작` | `MyRooms`와 `Note`는 남고 방 풀 인스턴스만 사라짐 |
| 자동 루트 안 사용자 오브젝트 | 자동 `Rooms` 아래 임의 오브젝트를 넣고 Room Root를 `MyRooms`로 바꿔 `새 실험 시작` | `Rooms`는 삭제되지 않고 경고 출력, 넣은 오브젝트 보존 |
| 파괴된 루트 | 지정한 `MyRooms`를 실험 도중 삭제 → `새 실험 시작` | `Room Root로 지정한 오브젝트가 파괴되어…` 오류, 다른 부모에 배치하지 않음. 비우거나 다시 지정 후 새 실험으로 복구 |
